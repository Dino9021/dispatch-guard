# 無人看管的工作（unattended-work 正體中文對照）

> ⚠ **這是給人讀的參考翻譯，不是 skill 本身。**
> skill 只讀同目錄的 [SKILL.md](SKILL.md)，英文版才是唯一有效的依據。
> 英文版更新後這份可能落後；兩邊不一致時以英文版為準。
> ⛔ 開場那一行確認句**必須照英文版原文印出**，不要印這份的翻譯。

**第一個輸出 —— 在任何事情之前，印出這一行：**

> ⭐ **`unattended-work` ACTIVE** — sequential dispatch · plan on disk before dispatch ·
> refute the fix, not just the code · stall test at 2 rounds · mutation-check every
> fail-open guard · exit bar before handing back.

那是 owner 用來分辨「skill 真的載入了」和「agent 只是掃過一個檔案」的唯一方法。
⛔ 如果你不打算遵守其中某一條，就說出是哪一條、為什麼，不要印那一行。

⭐ **這個 skill 要防的失敗不是「agent 什麼都沒做」**，而是**看起來完成了、其實是錯的、
而且很有自信的輸出**。⚠ **你專案自己的指示位階高於這個 skill**；專案檔案更嚴格的地方，
以嚴格的為準。

## 1. 派工

- ⭐ **預設循序，不論幾個都已經預先核准 —— 絕對不要問。** 送一個、等它、再送下一個。
- 並行需要 owner **真的送出過**的訊息裡的核准（核准 N 的意思是「同時 N 個活著」）。
  ⛔ **背景派工和大量生成工具是禁止的**，沒有核准管道。
  ⚠ 急、「這只是 review」、「agent 很便宜」、以及某個 skill 或工具說明叫你散開 —— 都不是核准。
- 要申請並行：寫好計畫、告訴 owner 數量，然後**立刻開始循序派工** —— 不要停下來等答案。

## 2. 計畫要在派工「之前」落到硬碟

- 先把每一個子任務的完整提示詞寫進檔案。⛔ 無條件 —— 不因為批次小、唯讀、或很明顯而省略。
- ⛔ **放「哪裡」不是你能選的，放錯會讓派工被拒絕。**
  如果這個專案帶了 `dispatch-protocol`，那個 skill 擁有這個佈局 —— 去讀它：提示詞放在
  `<task_root>/<task>/prompts*.md`（預設 `<repo>/Memory/tasks/`），而 hook 要找到一個
  比 session 開始時間新的 `prompts*.md` 才會允許派工。暫存檔案放在同一個任務資料夾底下，
  每個子任務一個目錄，⛔ 絕對不是共用的暫存路徑。
  ⚠ 少了這一點，agent 會把一份完全正確的計畫寫在 gate 看不到的地方，
  而拒絕訊息指的是一個它從來沒用過的路徑。
- 每一份提示詞都必須：
  1. ⛔ **完全獨立**（agent 沒有你的任何 context —— 不可以寫「如上所述」；每一個路徑、限制、
     驗收標準都要寫在本文裡）；
  2. **結尾指名它的輸出檔案**；
  3. ⛔ **要求報告「邊做邊寫」**（「把 `<path>` 建起來當作你的第一個動作，然後每有一個發現就附加」）。
     ⚠ 在最後一次寫入之前死掉的 agent，等於什麼都沒產出。

## 3. 一個完整的波次：實作 → **會執行的**反駁者 → 修正 → 把修正再送回去反駁

- ⛔ 反駁者必須**靠執行**來了結每一條線索，不是靠讀完然後下結論。
- 修完之後，**把修正再送一輪，包含你自己改的那幾塊** ——
  ⚠ 一個修正會針對「被指名的那個性質」最佳化，然後弄壞一個沒有人寫下來的性質。

## 4. 一個實質段落結束之後

- ⭐ **兩個強的審閱者，角度要不同，而且一個一個派。**
  ⚠ 審閱者的範圍就是它的盲區：兩個都回來之後，明確問一句「哪些是兩邊都沒看的？」
- 修掉他們找到的，然後問 adviser；修完再問一次；沒東西了 → ⭐ **直接繼續，不要問 owner。**
  ⚠ adviser 兩輪就是預算；還活著的阻塞項目走第 7 條。
- 這個環境沒有 adviser → 用第二個獨立、context 全新、任務是唱反調的子代理替代。
- ⭐ 同一天、同一個作者寫的東西也要接受對抗式審閱 —— 包含監督者自己改的部分。

## 5. 你猶豫的時候 —— 去辯論，不要用猜的

派**一個**有能力的子代理去找證據並給建議，摘要，然後問 adviser。

## 6. 你和 adviser 意見衝突 —— 再辯論**第二次**

⛔ 不要直接照做，也不要直接忽略。針對爭議點再派一個找證據的代理、摘要、再問一次 ——
⚠ 而且要明講：「我量到 X，你建議 Y，是哪一個限制決定勝負？」

## 7. **同一個問題**上第二次沒有結論 → 掛起，繼續走

把那個項目標成 pending；把**整場辯論**寫進檔案（雙方立場、每一輪拿到的證據、
這個決定真正取決於什麼）；然後移到下一個項目。
⭐ owner 會用他自己的時間決定掛起的項目 —— 這一輪繼續工作。

## 8. ⛔ 卡住判定

> **同一個項目連續兩輪沒有產生「新的、確認過的」發現，那個項目就是卡住了：
> 掛起（第 7 條）、記下它走到哪裡、換下一個。**

⚠ 「有進展」永遠感覺是真的；「確認過的發現」才檢查得出來。
⭐ 同樣的錯誤出現三次不是毅力，是迴圈。

## 9. ⛔ 一個守衛在「突變殺死它」之前都不算驗證過

對每一個**會 fail open** 的守衛（速率限制、過期檢查、權限測試、退避、「這樣安全嗎」的分支）：
**把守衛刪掉、看著檢查失敗**，才算驗證過。

⚠ 測試會用三種方式變瞎：失敗路徑產生的訊息剛好就是斷言在找的那個字；前置設定根本沒有走到
被斷言的路徑；⭐ **另一個守衛替被測的那個擋掉了** —— 要量其中一個，先關掉另一個。

## 10. 觸發條件是「你做出宣稱」，不是「你跑了檢查」

一句話如果宣稱某個**構得到的**系統做了什麼、在做什麼、將會做什麼，那就是一個驗證宣稱：
⛔ **先執行再開口，否則就明確標成猜測。**

⚠ 「每一個」「總是」「從不」「只有」是**量測**，不是語氣。
⭐ 名字不是本體，「程式碼存在」不等於「程式碼會跑」 —— 要回答「這件事會發生嗎」，**去找呼叫端**。

## 11. 空的結果是一個「宣稱」

固定路徑（一個 `cd` 會滲到之後每一次呼叫）。⛔ 絕對不要消音搜尋的錯誤（`2>/dev/null`、`-s`）。
管線會用管線的結束碼蓋掉原本的。⭐ 先證明工具真的跑了 —— 同一次執行裡放一個**正對照**。
⚠ **樣式本身也是工具**：搜尋「概念」，而且用兩種不同的寫法。

要回答「還有什麼沒做完」，⛔ **去搜尋「已完成」，永遠不要搜尋「未完成」**；
⚠ 一個你沒能確認的項目是**未確認**，不是**未完成**。
一個在鏈結裡安靜失敗的 `cd` 會讓「沒有輸出」跟「沒有符合」長得一模一樣。

## 12. 產生內容

⛔ 絕對不要把 commit 訊息放在命令列上（寫成檔案再 `-F`）。
⛔ 絕對不要用 heredoc 手寫長檔案（用寫檔工具）。
⛔ 絕對不要在產生的程式碼裡嵌入引號或反斜線 —— 改結構讓它不需要。
產生之後、執行或 commit 之前，**先用那個語言自己的剖析器跑一次**。
到處都明確指定 UTF-8。

⚠ 要知道遠端呼叫的另一端是哪個 shell，而且**絕對不要在遠端過濾** ——
把整份輸出帶回來、在本地過濾。⭐ 讀回「真正會被消費的那個東西」（編譯器看到的檔案、
log 顯示的訊息），不是你打的那行指令；懷疑亂碼時**用碼位判定，不要用眼睛看**。

## 13. Git

每一個 commit 都在同一口氣裡 push。
⛔ **每一次 commit 之前檢查分支**（`git rev-parse --abbrev-ref HEAD`）；
如果不是這個 session 建立或被指定的分支，**不要 commit —— 去問**。
⚠ 修正一個提交到錯誤分支的 commit，只能用一個丟棄式 clone 去 cherry-pick 你自己的那個
commit；⛔ 絕對不要切換共用的工作樹，也不要推到主幹。
commit 之前先篩掉憑證、金鑰、token 和機器識別碼。

## 14. ⛔ 出場門檻 —— 交回去之前每一行都要成立，不成立就說是哪一行

- [ ] 現有的每一個測試都綠，⭐ **而且指名是在哪一台機器上跑的**
- [ ] 每一個 fail-open 的守衛都做過突變檢查（第 9 條）
- [ ] 兩個審閱者的發現都修掉了，⭐ **而且修正也送回去再審過**（第 3、4 條）
- [ ] adviser 的第二輪回來是空的
- [ ] 沒有未解決的阻塞項目；每一個掛起的都寫下來了（第 7 條）
- [ ] 全部 commit 並 push（第 13 條）
- [ ] 報告裡每一個宣稱都是**執行過**的，不是推理出來的（第 10 條）
- [ ] ⛔ **你「沒有做」的事情寫下來了，連同理由** —— 安靜地縮小範圍是無人看管時的經典失敗

## 15. 排程與發問

⭐ **先做完所有不需要 owner 的事**；需要 owner 的項目排到隊伍**最後面**，不是對話最前面。
⛔ **除非 owner 必須實際去操作某個東西，否則不要問 —— 繼續做。**
⚠ 這拿掉的是「習慣性回報」，不是專案定義的任何核准關卡。
只剩下需要 owner 的項目時，⭐ 乾淨地停下來 —— 不要為了看起來很忙而發明旁邊的工作。

## 16. 停下來時的報告

⛔ **開頭就講 owner 必須「做」什麼，寫成具體步驟**（大約五步，不要術語、不要任務編號 ——
講畫面和按鈕的名字）；然後才是做了什麼；然後是有沒有成功。
⭐ 任何你自己做得到的步驟，就去做 —— 絕對不要把自己的工作當成待辦事項交回去。

## 17. context 快用完時的交接

說出來，並建議開一個新的 session —— ⛔ 不要硬撐到 context 在任務中間死掉。

先準備好：(1) 一份獨立可讀的交接文件（狀態、做過的決定、完成/未完成、試過但失敗的）；
(2) 下一個 session 的提示詞，存成獨立檔案，寫成完全不依賴這場對話。
⚠ **在寫下的當下重新驗證每一個引用的行號。**

## 18. 工作方式檢查表

**寫程式之前：** 複述任務邊界 · 列出用到的來源 · 列出你預期會改的檔案 · 列出風險和未決問題 ·
⚠ 如果改動碰到專案設有關卡的東西，等核准。

**寫的時候：** 小而可審閱的 diff · 加測試或明確的驗證步驟 · 保持既有命名與慣例。

**寫完之後：** 摘要改了什麼 · ⭐ 記下**跑過的測試「和沒跑的測試」** · 更新專案的狀態紀錄 ·
記錄任何新的決定。

## 19. 安裝

⭐ **外掛本身就是安裝。** 啟用 `dispatch-guard`，這支 skill 就在每個專案裡，
名字是 `dispatch-guard:unattended-work`。不用複製，不用部署。

⛔ **絕對不要建立 `~/.claude/skills/unattended-work/`，也不要任何第二份複本。**
同一個 skill 名字下有兩個檔案，而 session 到底載入了哪一個，從外面看不出來。
2026-08-27 實測：那兩份除了換行符號以外當天是逐位元組相同的，
而從外掛的下一次發布開始就會安靜地分岔。

改動要進 `dispatch-guard` 這個 repo，然後透過外掛更新送達。
⚠ 改在任何一份「已安裝的複本」上（包括 `~/.claude/plugins/` 底下的）都會被安靜地覆蓋掉。

開場提醒是外掛自己出的（`hooks/unattended.py`），
要關掉就設 `CLAUDE_PLUGIN_OPTION_ANNOUNCE_UNATTENDED_WORK=false`。
⛔ 不要再去 `settings.json` 加第二個提醒 —— 那會變成一則逐位元組相同的重複訊息。

⚠ session 開場沒有 ACTIVE 那一行 = 沒有東西載入它；
⭐ **hook 有觸發，不等於規則有被遵守** —— 印出來的那一行才是檢查。
沒印出來的話，就去「已安裝的外掛路徑」底下讀這個檔案，然後照樣遵守它。

## 20. 這個 skill 沒有涵蓋的

專案特有的規則（機器、誘餌、時間戳政策、安全不變量）—— ⚠ 專案自己的指示位階高於這個檔案。

決策治理（ADR 審的是**決定**，第 4 條審的是**程式碼**）。

⛔ **強制執行** —— 如果專案帶了一個會拒絕工具呼叫的 hook，
**那個 hook 的位階高於你對這個檔案的記憶**，而一次被拒絕的派工是規則在運作，不是 bug。
